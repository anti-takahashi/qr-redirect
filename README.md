# qr-redirect

アンティーク家具たかはしの**店の道具（静的ファイル）の置き場**。
公開先 `https://qr.antiquekagu-takahashi.com/`

> ⚠️ 名前は「redirect」のままだが、中身は中継ページではない。
> 2026-07-29に**カタログ本体ごと引っ越して**、中継の役割はカタログが吸収した（下記）。
> リポジトリ名を変えると GitHub Pages の設定を作り直すことになるので、名前は据え置く。

## なぜここにあるのか

印刷したQRのURLは二度と変えられない（ラベルは何年も貼りっぱなし）。
行き先を直接焼き込むと、その行き先が使えなくなった日にラベルが全部死ぬ。

しかも、これまでの置き場だった自社EC（`antique-takahashi.com`）は
**DNSがEC事業者(iFLAG)配下**で、**EC契約が切れるとネームサーバーごと止まる**。

このドメイン（`antiquekagu-takahashi.com`）は**オーナー名義・Squarespace管理**で、
EC契約と無関係に生き続ける。
→ **当社が握るドメインへ、店の道具を1か所に集める。**

- ラベルに焼くのは `https://qr.antiquekagu-takahashi.com/?t=<32桁16進>` **だけ**
- ⚠️ **置き場（GitHub Pages）はいつでも変えてよい。変えてはいけないのはドメインの方**
- 🔴 **`CNAME` を消さない・変えない。** 消すとカスタムドメインが外れ、
  **印刷済みラベルの行き先が消える**

## 何が置いてあるか

| URL | 中身 | 原本（業務リポジトリ側） |
|---|---|---|
| `/`（`/?t=<32桁>`） | 商品カタログ本体。**印刷済みQRの着地点** | `qr_inventory/catalog-site/index.html` |
| `/data.json` | カタログの公開用データ | `qr_inventory/catalog-site/data.json` |
| `/404.html` | 見つからないURLの受け皿。パス形式 `/<32桁>` も拾う | `qr_inventory/catalog-site/404.html` |
| `/quickreg/` | かんたんQR登録（店内・現物の前で使う） | `qr_inventory/quickreg/` |
| `/capture/` | ターンテーブル撮影 | `qr_inventory/capture/index.html` |
| `/line-login.html` | 公式LINEログインの戻り先（中継） | `qr_inventory/line_cb/cb.html` |

**原本はここではない。** ここは公開用の写しで、業務リポジトリ側から
`tools/qr_site_publish.py` が同期して push する。**このリポジトリを直接編集しない。**

### 中継ページはどこへ行ったか

以前は `index.html` が中継ページで、`?t=` を受けて自社ECのカタログへ飛ばしていた。
カタログ自体をここへ置いたので、**1ホップ減って中継が要らなくなった**。
中継が持っていた「トークンが無い／形が違うときの案内」はカタログ側が引き継いでいる
（行き止まりを作らない）。**行き先を後から変えられるという利点はそのまま**
＝このリポジトリの中身を差し替えればよい。

## 決まりごと

- **秘密情報を入れない**（公開リポジトリ）。`data.json` は公開用データだけを載せる
  ホワイトリスト方式の書き出しを通っている
- 🔴 **git の履歴は消えない。** FTPと違い、一度 push したものは
  **公開し直しても取り消せない**。だから書き出し側の検算を絶対に弱めない
- 改行は **LF固定**（`.gitattributes`）。Windows側の `core.autocrlf=true` で
  作業コピーがCRLFになると、1文字も直していないのに公開物のmd5が変わる
